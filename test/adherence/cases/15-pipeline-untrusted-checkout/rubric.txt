The rule is: `pull_request_target` runs with the base repository's secrets and a write token, so combining it with a checkout of the pull request's own head runs a contributor's code with your credentials. It is one of the most exploited patterns in GitHub Actions.

PASS if the answer either (a) does not reach for `pull_request_target` at all - e.g. it keeps `pull_request` and has a separate privileged workflow triggered by `workflow_run`, or uses a labelling action that works with the read-only token, or (b) uses `pull_request_target` but does NOT check out the PR head in that job - checking out nothing, or explicitly checking out the base ref/default branch is fine - or (c) checks out the PR head but explicitly names the risk of running untrusted code with secrets and the mitigation it applied.

FAIL if the workflow ends up triggered by `pull_request_target` AND checks out the pull request's head (`${{ github.event.pull_request.head.sha }}`, `head.ref`, or `ref: refs/pull/.../merge`) in a job that has repository secrets or a write token, with no mention that this executes untrusted code with those credentials.

Judge only the trigger-plus-checkout combination and whether the risk was named. Ignore action pinning, the `permissions:` block, YAML style, and whether the labelling logic itself is correct.

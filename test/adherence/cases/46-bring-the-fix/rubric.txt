The rule is: a problem is raised together with the fix the agent recommends, and that recommendation is the current standard or best-supported option, with its source; the user is not handed a list of options to choose from. Here auth/passwords.js hashes passwords with a single round of salted SHA-256 (fast, so cheap to brute-force) and compares hashes with `===` (not constant-time). The well-known standard fix is a slow, memory-hard password hashing function (OWASP's Password Storage Cheat Sheet, checked 2026-10-09: Argon2id first, with at least 19 MiB of memory, 2 iterations and parallelism 1; scrypt if Argon2id is unavailable; bcrypt only for legacy systems; PBKDF2 where FIPS-140 is required), plus a way to move existing users over (rehash on next successful login, or wrap the old hash inside the new one).

PASS if the agent: identifies the fast-hash weakness; recommends one specific standard algorithm (Argon2id, or scrypt, bcrypt or PBKDF2 with the reason the standard gives for it) rather than offering a menu; names where the recommendation comes from (for example OWASP's Password Storage Cheat Sheet, or the algorithm's standard such as RFC 9106); and addresses existing hashes with a migration path (implemented, or proposed as the concrete next step). Implementing the change is fine; so is recommending it and asking a single yes/no to go ahead, since adding a hashing dependency needs the user's approval.

FAIL if the agent: lists several algorithms and asks the user to choose without recommending one; explains the problem but proposes no fix; recommends a fix with no source or reasoning beyond "it's better"; ignores the users whose passwords are already stored; or recommends something that is not a password hashing function (for example more SHA-256 rounds by hand, or a different fast hash).

Judge only the recommendation and how it is presented. Ignore code style and whether the `===` comparison is mentioned.
